## Summary

An instance can pick a garbage collector preset (Default, Serial, Parallel, G1, ZGC, ZGC
Generational, Shenandoah). The picker — CLI and GUI — offers only collectors the Java that
instance launches with actually supports, found by running that JVM once and parsing
`-XX:+PrintFlagsFinal`. Launch applies the matching flags and refuses to start rather than pass
Java a collector it does not have. Spec: `docs/superpowers/specs/2026-09-08-gc-presets-design.md`
(approved; the user chose "download the runtime and probe it" over refusing when no Java is
present yet).

## Design seams settled here

These resolve gaps the spec left open (module ownership, the config-default's exact meaning,
which command runs the probe). Read this section before Task 1; it is binding, not a suggestion.

- **`GcPreset` lives in `instances::model`, not `launch` or `java`.** The spec names either as
  acceptable. `ARCHITECTURE.md`'s dependency table has `instances` depending on `paths`,
  `settings`, `sources`, `download` — not `java` — and `java` depending on `download`, `http`,
  `paths` — not `instances`. `InstanceJvm.gc: GcPreset` needs the type visible from `instances`;
  `java::gc::probe`'s result needs to be checked against it from `launcher`, which already depends
  on both. Putting `GcPreset` in `instances::model` (next to `InstanceJvm`, which already owns
  `extra_args` and `java_path`) costs no new edge in the dependency graph. `launch::command`
  already imports `crate::instances::Instance`, so it can name `GcPreset` too, with no new edge
  either. `java::gc` stays free of any `instances` dependency by returning **raw** probe data
  (`GcSupport { major: u32, flags: BTreeSet<String> }` — the flag *names* `-XX:+PrintFlagsFinal`
  printed, not `GcPreset` values); `instances::model::supported_presets(major, &flags) ->
  Vec<GcPreset>` is the pure translation function, callable from `launcher` (which holds both
  types) and unit-tested with a hand-built `flags` set, no process spawn needed. Update
  `ARCHITECTURE.md`'s `instances` row to add a "GC presets" clause in Task 6, not before — do not
  let this note substitute for that edit.
- **`config.jvm.gc` is a creation-time seed, not a launch-time fallback.** Heap bounds use
  `Option<u32>` in `InstanceJvm` so "unset" can fall back live to `config.toml` at every launch
  (`instance.config.jvm.min_mib.unwrap_or(config.jvm.min_mib)` in `launcher::prepare_launch`).
  The spec gives `InstanceJvm.gc` the bare type `GcPreset` with serde default `Default`, not
  `Option<GcPreset>` — there is no "unset" state to fall back from once an instance exists.
  `config.jvm.gc` (new field on `config::JvmDefaults`, changed by `gcl config set-jvm --gc`)
  therefore seeds a **new** instance's `jvm.gc` at `Instances::create`, the same way
  `config.game_defaults` seeds a new instance's `options.txt` preseed — not something the launch
  path reads again. Document this once, in the doc comment on `InstanceJvm.gc`, so a future
  reader does not "fix" it into a live fallback and silently change what a saved preset means.
- **The probe is one JVM invocation, reusing the existing property-dump path.**
  `java::detect::probe` already runs `-XshowSettings:properties -version` and parses the
  `java.version =` line for the major version. `java::gc::probe` runs
  `-XshowSettings:properties -XX:+PrintFlagsFinal -version` — one process, both flags accepted
  together — and parses the same `java.version` line for `major` (reusing
  `detect::parse_java_version`) plus a new line parser for the flags dump. A
  `-XX:+PrintFlagsFinal` line is whitespace-columns:
  `     bool UseG1GC                                  = true                    {product}`;
  the flag name is the **second** whitespace-separated token (the first is the C++ type: `bool`,
  `intx`, `uintx`, ...). Collect every second token from a line whose first token is a bareword
  type name (skip banner/header lines that do not start that way) into `GcSupport.flags`, no
  matter whether the value is `true` or `false` — presence in the dump means the JVM's build
  compiled that collector in, which is what "supported" means here; the value only says whether
  it is the one active by default. `java::gc` is a plain `tokio::process::Command` call with the
  same `PROBE_TIMEOUT` (10 s) `detect::probe` uses, not the `ProcessRunner` trait: `ProcessRunner`
  exists so Forge/NeoForge installer processors can be faked without a real JVM in a unit test
  (`crate::loaders::processors`); a GC probe is not an installer step and has no processor-style
  "writes files, returns an exit code" contract to fake — the flow test's stand-in `fake-java`
  shell script is this seam's test double, the same way it already stands in for the real launch
  command.
- **Cache: an in-process map plus one JSON file, both keyed by `(canonical path, mtime)`.**
  `java::gc::ProbeCache` holds `Mutex<HashMap<(PathBuf, i64), GcSupport>>` and is constructed once
  as a `Launcher` field (`gc_cache: java::gc::ProbeCache`, next to the existing `icons`/`images`
  cache fields — same shape, an `Arc`-free plain field since `Launcher` itself is handed out as an
  `Arc`). `ProbeCache::get_or_probe(cache_file, java_path)`: canonicalize `java_path`, read its
  mtime, check the in-memory map first, then the on-disk `cache/runtimes/gc-probe.json` (a JSON
  array of `{ path, mtime, major, flags }` records — plain enough that a human can read it, and
  small enough that "the whole file, decode, re-encode" is not a real cost here), and only then
  run `probe()`; every hit updates the in-memory map, and a miss appends to and rewrites the disk
  file via `paths::write_atomic`. A path whose mtime moved (a JVM this launcher itself replaced by
  installing a newer runtime under the same directory, or someone editing `JAVA_HOME` in place) is
  treated as a fresh probe, not a stale hit.
- **Launch-time validation and flag insertion is real code in two places, not a TODO.** In
  `Launcher::prepare_launch` (after the existing `java: PathBuf` resolution, before
  `launch::build` is called): probe the resolved `java` through `gc_cache`, get `GcSupport`, and if
  `instance.config.jvm.gc != GcPreset::Default` and it is not in
  `instances::model::supported_presets(support.major, &support.flags)`, fail with
  `java::Error::UnsupportedPreset { preset: String, java: PathBuf, major: u32 }` (a new variant;
  it flows to the caller through the existing `crate::Error::Java(#[from] ...)` wrapper, no new
  top-level `Error` variant needed) before `launch::command::build` ever runs — this is the "probe
  runs again (cached) and a preset the JVM lacks is a launch error before spawn" line in the spec.
  `JvmSettings` (in `launch::command`) gains `pub gc: GcPreset` and `pub gc_major: u32` (the major
  the probe just found, not `plan.java_major`, since a manually configured `java_path` carries no
  major of its own); `launch::command::build` calls `gc.flags(gc_major)` itself — `GcPreset` is
  already visible there — and inserts the result right after the two heap flags
  (`-Xms.../-Xmx...`) and before `inputs.jvm.extra_args`. A pure helper,
  `gc_conflict(gc: GcPreset, extra_args: &[String]) -> Option<&str>`, returns the first
  `extra_args` entry that looks like a hand-written collector choice
  (`-XX:+UseSerialGC`/`-XX:+UseParallelGC`/`-XX:+UseG1GC`/`-XX:+UseZGC`/`-XX:+UseShenandoahGC`/
  `-XX:+ZGenerational`/`-XX:-ZGenerational`) whenever `gc != GcPreset::Default`; `build()` turns a
  hit into `launch::Error::GcConflict { preset: GcPreset, extra_flag: String }` before it ever
  reaches java. Both are ordinary pure-function unit tests, no process spawn, per the `testing`
  skill's "pure helper first" rule.
- **`Launcher::gc_support(slug)` reuses `configured_or_detected_java`'s exact resolution order**
  (instance `java_path`, else `config.jvm.java_path`, else `java_for_version(mc)`, which installs
  a Mojang runtime with the normal progress events when nothing local matches) rather than
  inventing a second resolution path — this is the literal wording of the design doc ("resolves
  the Java the instance launches with... using the same code the launch uses"). Unlike
  `configured_or_detected_java`'s existing early-return for a *configured* path (which fabricates a
  placeholder `JavaInstall` with `major: 0` and never probes it), `gc_support` always runs the
  cached probe afterward regardless of where the path came from, since the whole point is to learn
  the real major and flag set of whatever binary answers at that path. It returns a small public
  view type, `GcSupportView { java_path: PathBuf, label: String, major: u32, presets:
  Vec<GcPreset> }`, where `label` is built the same way `InstanceSummary`'s existing "Java path
  that would be used" text is (see `installer_java`/`instance_summary` for the pattern) plus the
  probed version string, e.g. `"Java 21.0.4 from the Mojang runtime"`.

## Risks

- **A `-XX:+PrintFlagsFinal` line format is not perfectly stable across JDK vendors and
  versions.** The parser reads "second whitespace token on a line whose first token looks like a
  C++ type name", which is loose by design rather than matching an exact column width (real
  `PrintFlagsFinal` output right-aligns names to the longest one in the dump, so a fixed-column
  parse breaks the moment a longer flag name appears anywhere in the file). Mitigation: Task 2's
  three fixtures are real dumps from three different JDK builds already on this machine (17, 21,
  25), which is the best available cross-version check without a CI matrix of JDKs; a future
  vendor mismatch would show up as an empty `flags` set (every preset but `Default` reported
  unsupported) rather than a wrong answer, which is a safe failure mode — a picker that offers too
  little is a worse UX, not a broken launch.
- **The disk cache (`cache/runtimes/gc-probe.json`) can grow unbounded if a machine accumulates
  many different java paths over time** (every Mojang runtime component, every `JAVA_HOME` a user
  ever pointed at). Mitigation: each record is a few dozen bytes; this is not a meaningfully large
  file even at dozens of entries, and no plan task here adds pruning — flagged so a future plan
  does not have to rediscover that the file has no eviction policy.
- **The launch-time re-probe adds one JVM spawn to every launch that has a non-`Default` GC preset
  saved**, even though the cache usually answers instantly. Mitigation: this is the explicit
  "probe runs again (cached) and a preset the JVM lacks is a launch error before spawn" line in
  the approved spec, not a design choice this plan is free to skip — the alternative (trusting a
  stale cached answer at launch) risks starting Java with a flag it does not have, which is a
  worse failure (a crash after the user pressed Play) than one extra fast process spawn.
- **`GcPreset` living in `instances::model` rather than `launch` or `java` is a deliberate
  departure from the spec's literal wording** ("in `gcl-core::launch` (or `java`)"). Mitigation:
  "Design seams settled here" above lays out exactly why, citing `ARCHITECTURE.md`'s existing
  dependency table; Task 8's `ARCHITECTURE.md` update makes the real placement visible to anyone
  who only reads the architecture doc and not this plan.
